### Naming Conventions:

AKO Gateway Implementation follows the following naming conventions:

  1. **ParentVS**: `ako-gw-<cluster-name>--<gateway-namespace>-<gateway-name>-EVH`
  
  2. **ChildVS**: 
     - **With Named Route Rules** (AKO 2.1.1+, Gateway API v1.3+): `ako-gw-<cluster-name>–-<sha1 hash of <gateway-namespace>-<gateway-name>-<route-namespace>-<route-name>-<stringified FNV1a_32 hash of bytes(rulename)>>`
     - **Without Named Route Rules** (Legacy): `ako-gw-<cluster-name>–-<sha1 hash of <gateway-namespace>-<gateway-name>-<route-namespace>-<route-name>-<stringified FNV1a_32 hash of bytes(jsonified match)>>`
  
  3. **Pool**: 
     - **With Named Route Rules** (AKO 2.1.1+, Gateway API v1.3+): `ako-gw-<cluster-name>--<sha1 hash of <gateway-namespace>-<gateway-name>-<route-namespace>-<route-name>-<stringified FNV1a_32 hash of bytes(rulename)>-<backendRefs_namespace>-<backendRefs_name>-<backendRefs_port>>`
     - **Without Named Route Rules** (Legacy): `ako-gw-<cluster-name>--<sha1 hash of <gateway-namespace>-<gateway-name>-<route-namespace>-<route-name>-<stringified FNV1a_32 hash of bytes(jsonified match)>-<backendRefs_namespace>-<backendRefs_name>-<backendRefs_port>>`
  
  4. **PoolGroup**: 
     - **With Named Route Rules** (AKO 2.1.1+, Gateway API v1.3+): `ako-gw-<cluster-name>–-<sha1 hash of <gateway-namespace>-<gateway-name>-<route-namespace>-<route-name>-<stringified FNV1a_32 hash of bytes(rulename)>>`
     - **Without Named Route Rules** (Legacy): `ako-gw-<cluster-name>–-<sha1 hash of <gateway-namespace>-<gateway-name>-<route-namespace>-<route-name>-<stringified FNV1a_32 hash of bytes(jsonified match)>>`
  
  5. **SSLKeyAndCertificate**: `ako-gw-<cluster-name>--<sha1 hash of <gateway-namespace>-<gateway-name>-<secret-namespace>-<secret-name>>`
  
  6. **DefaultHTTPPolicySet**: `ako-gw-<cluster-name>--default-backend`

#### Readable object names

When `AKOSettings.useReadableObjectNames` is set to `true`, Gateway API object names change in three ways.

**The `ako-gw-` prefix is dropped from the name.** Object ownership is carried by `created_by`, which stays `ako-gw-<cluster-name>` and is what every cache and garbage collection query filters on. The prefix was doing no ownership work in the name itself, so names become `<cluster-name>--...`, the same shape the AKO ingress container already uses.

**Each `<sha1 hash of X>` becomes a readable head plus a short hash**, `<readable>-<first 8 characters of that same sha1 hash>`. The hashed input is unchanged, so uniqueness is unaffected.

**The name leads with the surface the route serves**, taken from the `ai.ako.vmware.com/surface` label on the HTTPRoute:

| Label value | Token | Meaning |
| --- | --- | --- |
| `llm`, `inference` | `llm` | An inference route to a model backend |
| `mcp` | `mcp` | An MCP tool server route |
| `agent`, `a2a` | `agent` | An agent to agent route |
| absent or unrecognised | none | An ordinary HTTPRoute |

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: mcp-web
  namespace: mcp
  labels:
    ai.ako.vmware.com/surface: mcp
```

giving, for cluster `openshift06`:

```
openshift06--mcp-mcp-mcp-web-tools-8c7e0d22
openshift06--agent-agents-log-collector-a13f9e07
openshift06--llm-ai-gw-llm-chat-3f9a1c2b
openshift06--default-shop-checkout-11ee9042
```

The surface leads the name so that the Avi UI's name-sorted virtual service list groups by surface, and so that the token can never be the part lost to truncation. The parent gateway is deliberately left out of the readable head - a child VS is always read underneath its parent - but it is still part of the hashed input, so two routes that differ only in gateway still get different names.

The surface is read from a label on the route rather than inferred from an attached `AIMCPRoutePolicy` or `AIA2ARoutePolicy`. Those policies reach AKO through informer events that are not ordered against route processing, so inferring the surface would give a route one name on one restart and a different name on the next, and a rename is a delete and a recreate.

Independently of this flag, the surface is always emitted as an Avi `Surface` marker, so routes can be filtered by what they are even while their objects are still SHA1 named.

The `PKIProfile` name generated for `ako-crd-operator` interop is always a bare digest in both modes, because it has to match a name generated by a separate module that does not see this setting.

The flag is shared with the AKO ingress container and is an install time choice: see [AKOSettings.useReadableObjectNames](../values.md#akosettingsusereadableobjectnames).
